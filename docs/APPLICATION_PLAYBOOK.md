# IT導入補助金 申請 Playbook
## 受発注Lシステム → 複数ベンダー横展開のための総合ガイド

本書は、IT導入補助金（デジタル化・AI導入補助金）の ITツール登録申請にあたり、
本リポジトリ（`claude/create-marketing-materials-FirCs` ブランチ）で構築した
受発注Lシステムと申請用マーケティング／申請書類一式の**全体像を記録**し、
今後「ITツール名」「申請ベンダー名」等を差し替えた**複数申請フローへの横展開**を
容易に行えるようにすることを目的とした playbook である。

---

## 2. 構築物の全体像

本プロジェクトは **「1つのNext.jsアプリ」** に以下の3つの機能群が同居している:

1. **システム本体**（認証付き業務アプリ）
   - 発注書・請求書の作成／承認／印刷、取引先／案件／ユーザー／監査ログの管理
   - 実装箇所: `src/app/(dashboard)/...`, `src/app/auth/login/...`, `src/app/api/...`

2. **マーケティングLP**（公開・認証不要）
   - サービス紹介ランディングページ
   - 実装箇所: `src/app/(public)/lp/page.tsx`

3. **補助金申請資料セット**（公開・認証不要・A4印刷最適化）
   - 機能説明資料／価格説明資料（2バリアント）／申請価格理由書／その他要件説明／適格請求書サンプル／申請資料インデックス
   - 実装箇所: `src/app/(public)/subsidy/...`

これらを **ホスト名で振り分け** ている:
- `lsystem.let-inc.net` → LP＋申請資料のみ公開（システム機能へは自動リダイレクト）
- `jyuhacchu-system.vercel.app` → すべて公開（システム本体はログイン必須）

### 3-5. デプロイフロー（GitHub → Vercel 自動連携）

**本プロジェクトは GitHub と Vercel が連携済みで、GitHub の対象ブランチに push
すれば Vercel が自動的にビルド・本番反映**します。**ターミナルからの
`vercel deploy` は原則使用しません**（かつて使用していた `vercel link` /
`vercel env pull .env.production.local` / `vercel deploy --prod` の一連の
手順は非推奨。実施の必要なし）。

#### 標準的な反映手順（コード変更時）

```bash
# ローカルで修正・コミット・push するだけ
git add -A
git commit -m "..."
git push origin <対象ブランチ>
```

push 後、Vercel が数十秒〜数分で自動的にビルド → 本番デプロイ → カスタムドメイン
（`lsystem.let-inc.net`）にも即反映。

#### Production Branch

Vercel の Production Branch 設定に紐づいたブランチが本番デプロイ対象になります。
現状は `claude/create-marketing-materials-FirCs` が Production Branch。
`it-hojo` は開発用ブランチとして並行運用しており、両ブランチを常に同期させる
運用（`git checkout <他方> && git merge --ff-only <対象>`）を継続。

将来的に運用を単純化するなら、Vercel ダッシュボード → Project → Settings → Git
から **Production Branch を `it-hojo`（または任意の main）に一本化** することを
推奨。

#### 環境変数

環境変数（`DATABASE_URL`、`NEXTAUTH_SECRET` 等）は **Vercel ダッシュボード側で
管理**しており、ローカルの `.env.production.local` に依存しません。修正が必要な
場合は Vercel ダッシュボード → Project → Settings → Environment Variables で
直接編集し、再デプロイ（自動 or 手動トリガ）で反映。

#### 例外: DB のシード再投入だけはターミナル操作が必要

`prisma migrate reset --force` のような **DBへの直接操作** はコードの push では
反映されないため、必要な場合のみローカルターミナルから DATABASE_URL を渡して
実行します（DATABASE_URL は Vercel ダッシュボードから取得してコピペ）。
これは審査用のシード再投入等、稀な運用時のみ発生。

## 7. 新規申請時の作業フロー（段階別）

別ツール・別ベンダーで新たな申請を行う際の標準手順。
初見時は **0.5〜1日** 程度で一通りの資料刷新が可能な粒度で設計している。

### Phase A: 準備（所要 2時間）

1. **新ツールの基礎情報をシートにまとめる**
   - §5 で列挙した全変数（TOOL_NAME 〜 CASE2_AFTER_1）の値を確定
   - 特に「開発メーカー名」「IT導入支援事業者名」「所在地」「電話」「メール」は
     法務面で正確な表記が必要
2. **新ドメインの準備**
   - カスタムドメインを使う場合: サブドメイン設計を決める（例: `shinki-tool.let-inc.net`）
   - 使わない場合: 既定の Vercel URL（`xxx-system.vercel.app`）で運用
3. **既存スクリーンショット流用の可否を判断**
   - 新ツールが受発注系なら流用可能
   - 別業種／別機能なら、同じ11枚を新ツール画面で撮り直す必要あり

### Phase B: リポジトリ準備（所要 30分）

4. **本リポジトリをフォーク or 新規クローン**
   ```bash
   git clone <本リポジトリURL> <新ツールslug>
   cd <新ツールslug>
   git checkout -b apply/<新ツールslug>
   ```
5. **ブランチ運用方針の決定**
   - 本リポジトリから分岐させる場合: このブランチ `claude/create-marketing-materials-FirCs` を起点に新ブランチを切る
   - 別リポジトリを立てる場合: ブランチ `main` として運用開始

6. **環境変数の複製**
   - `.env.local` に既存と同等の値を設定（新ドメイン・新DBの値に更新）
   - Vercel プロジェクトを新規作成し、環境変数を設定

### Phase C: 変数書換（所要 3〜4時間）

§6 の編集ファイルマップに沿って置換を実施。**実行順序**を意識すると手戻りが少ない。

7. **ブランド系の一括置換**
   ```bash
   # 例: 受発注Lシステム → 新ツール名
   git grep -l "受発注Lシステム" | xargs sed -i "s/受発注Lシステム/<NEW_TOOL_NAME>/g"
   git grep -l "株式会社LET" | xargs sed -i "s/株式会社LET/<NEW_DEV_MAKER>/g"
   git grep -l "株式会社TX\.企画" | xargs sed -i "s/株式会社TX\.企画/<NEW_IT_SUPPORT_VENDOR>/g"
   ```
   ただし一括置換後は**必ず手目視でレビュー**（法務ページ本文や比較表の説明で文脈的に不自然になる箇所がないか）。

8. **価格・料金の書換**
   - `pricing-document.tsx` の `250,000` / `3,000,000` / `125,000` / `1,500,000` を新値に
   - `pricing/rationale/page.tsx` 内の同じ値（複数箇所）＋補助金自己負担額試算表も連動更新
   - LP の `#pricing` セクション表も更新

9. **導入事例の書換**
   - `pricing-document.tsx` の §導入事例・実績 内の Case 1 / Case 2 を実名・実数値に差替
   - 「仮例示」等の注記は入れない（審査で不合格になる）

10. **Pコードが変わる場合**
    - `requirements/page.tsx` の表と選択方針段落
    - `feature/page.tsx` の表紙／§1
    - `DocumentShell` への `pcode` プロップ
    - 申請画面の「ITツールに含まれる機能概要」「機能説明資料の該当ページ」もあわせて再執筆

11. **ドメイン設定の更新**
    - `next.config.ts` の `MARKETING_HOST`
    - `src/middleware.ts` の `MARKETING_HOST` / `SYSTEM_FALLBACK_HOST`
    - Vercel の Domains 設定
    - DNSレコード追加（CNAME → `cname.vercel-dns.com`）

### Phase D: 画像差替・ビルド（所要 1〜2時間）

12. **スクリーンショット撮影・配置**
    - `public/images/subsidy/` 配下に同じファイル名で11枚を配置
    - ダッシュボード・一覧画面・新規作成画面・印刷プレビュー・監査ログ等
    - 撮影条件: Chrome 1280〜1440px 幅、長辺1920px以内PNG
    - 画像未配置の Figure は点線プレースホルダに自動フォールバック

13. **ビルド検証**
    ```bash
    npm install
    npx prisma generate
    SKIP_ENV_VALIDATION=1 DATABASE_URL=... NEXTAUTH_SECRET=... NEXTAUTH_URL=... npx next build
    ```
    全ページが ○（Static）で正常に生成されることを確認。

14. **ローカル起動で目視確認**
    ```bash
    npm run dev
    ```
    - `/lp` → LPが新ツール名で表示されるか
    - `/subsidy` → 各資料に到達できるか
    - `/subsidy/feature` → 表紙の「ITツール名」「開発メーカー名」が大きく表示されているか
    - `/subsidy/pricing/tx` → 「IT導入支援事業者名」が正しいか
    - `/subsidy/pricing/rationale` → 実数値が入っているか
    - `/subsidy/invoice-sample` → サンプル請求書が表示されるか

15. **本番反映（GitHub → Vercel 自動デプロイ）**
    ```bash
    git add -A
    git commit -m "..."
    git push origin <Production Branch>
    ```
    push すると Vercel が自動的にビルド → 本番反映（数十秒〜数分）。
    `vercel deploy` コマンドは使用しない。反映確認は Vercel ダッシュボードの
    Deployments タブ、または `curl -I https://lsystem.let-inc.net/subsidy/...` で
    HTTP/2 200 が返ることを確認。

16. **PDF出力の検証**
    各資料ページで Ctrl+P／⌘+P → 「PDFとして保存」で A4 印刷プレビューを確認:
    - 表紙の黒塗りヘッダが正しく印字される
    - SVG業務フロー図が途切れず1ページに収まる
    - 類似ITツール比較表が別ページで明確に表示される
    - 10MB 以下に収まる（機能説明資料は画像11枚含むので最もリスク高）

### Phase E: 申請・不備対応（所要 1〜3週間／審査回転次第）

17. **補助金 事業者向けポータルにログイン（GビズIDプライム）**
    - ITツール登録新規申請
    - 各画面を本 playbook の「申請画面入力チェックリスト」（§10）どおりに入力

18. **PDFをアップロード**
    - 機能説明資料 → `/subsidy/feature` の PDF
    - 価格説明資料 → `/subsidy/pricing/tx` の PDF
    - 申請価格理由書 → `/subsidy/pricing/rationale` の PDF
    - インボイス説明資料 → `/subsidy/invoice-sample` の PDF
    - その他説明資料（任意） → `/subsidy/requirements` の PDF

19. **不備指摘への対応**
    - 不備メールを受けたら、本 playbook §8 の過去事例と照らし合わせ
    - 該当する .tsx を修正 → git push → Vercel 自動デプロイ → PDF再生成 → 再アップロード
    - 対応1回あたり 1〜2時間が目安

20. **採択後**
    - ITツール情報（価格・機能）に変更が発生した場合、本リポジトリで更新後に PDF を再提出
    - 補助金公募要領の改定（年度更新）が出たら要件再確認

### 8-7. 本申請で得た教訓（次回の申請に活かすべき点）

1. **背景色に依存した装飾はNG**
   審査員はブラウザの「背景のグラフィック」チェックを外した状態で印刷した PDF を
   見ている可能性がある。オレンジ背景ボックス等で識別情報を表現すると、白い四角しか
   残らず**「確認できない」と判定される**。
   → 今後も **黒塗り反転＋2pxボーダー＋大型太字フォント** を採用する。

2. **業務フロー図は HTMLリスト ≠ 図**
   審査員は「業務フロー図」として**矢印のあるビジュアル**を期待している。
   HTMLの縦並びリストは「フロー図」と認識されない。
   → SVG で箱と矢印を描画する。図番号「［図1］」を明記する。

3. **「仮例示」は絶対NG**
   「※ 将来公開分も含む仮例示です」のような注記があると導入実績と認められない。
   → 実名1件以上を必須。想定顧客として載せる場合も「想定顧客」と明記し、数字は根拠をもって記載。

4. **カテゴリーの混在に注意**
   SaaSの価格に「サポート・保守」を含めると、カテゴリー7（保守サポート）と
   カテゴリー1〜6（ソフトウェア）の混在とみなされる。
   → **ソフトウェア価格の説明には「保守サポート」「カスタマーサポート」「障害対応」等の
   役務的な文言を入れない**。運用インフラコスト（ホスティング・SSL・API利用料等）は許容される。

5. **類似ITツール比較は必須**
   「リリース直後の開発費用の資金回収計画」や「マーケットに対する希少性」のみでは
   不十分。**競合製品との価格・機能比較表**が無いと再審査で落ちる。
   → 最低4カテゴリ、◎○△— 評価軸5つ以上の比較表を用意する。

6. **PDF印刷時の改ページ制御**
   重要セクション（業務フロー図、類似ITツール比較など）は `page-break-before` を
   付与して**別ページ単独で視認できる**ようにする。

7. **「目次」と「章扉ページ」が必須**
   3回目の指摘で判明: 表紙のみではなく、**目次ページ＋各章の章扉ページ**を
   必ず用意する。特に審査で必須項目とされる「業務フロー図」「ITツールの利用方法」は
   それぞれ独立した章扉ページ＋本文見出しを黒帯／反転表示にし、一目で目的セクションに
   到達できるようにする。

8. **比較表は「具体製品名＋提供企業名」で書く**
   「○○相当」「△△系」のような抽象表現は審査員に**具体性なし**と判定される。
   実在する製品名（例: Oracle NetSuite, マネーフォワード クラウド請求書 Plus,
   ANDPAD 受発注, ジョブカンワークフロー 等）を**10件程度**列挙し、提供企業名・
   公表価格・機能比較軸を明記する。注釈で「2026年4月時点の公表価格・公開資料ベース」
   と免責を加えることで法務リスクを回避する。

9. **DocumentShell ヘッダ（毎ページ右上）に識別情報を載せる**
   表紙だけに頼らず、A4印刷時に各ページの**右上**に「ITツール名・開発メーカー名」を
   常時表示することで、審査員が任意のページから資料を参照しても正体がわかるように
   する。本実装では `DocumentShell` の `toolName` / `makerName` プロップで集中管理。

10. **共P-02 を選んだら「受発注機能」を専用ページで明示する**
    4回目の指摘で判明: Pコード「共P-02」を選択している場合、ITツール登録要領
    「2-3 (1) 4. 『会計』『受発注』『決済』のいずれかを有する」に基づき、
    **「会計／受発注／決済」3機能の有無表＋本ツールが受発注機能を有する旨**を
    専用ページとして明示する必要がある。「機能詳細」の中で受発注に触れるだけでは
    不十分。3機能の比較表と、受発注機能を構成する具体的な実装の列挙が必須。

11. **「取引年月日」は請求書発行日とは別物**
    インボイス制度上、「取引年月日」=「課税資産の譲渡等の年月日」=
    役務提供完了日／商品引渡日 を指す。**請求書発行日や納品書発行日は
    『取引年月日』として認められない**。サンプル帳票には:
    - ヘッダに独立した「取引年月日」フィールド
    - 明細表に独立した「取引年月日」カラム
    の2箇所に明示する。さらに必要記載事項チェックリスト表で「該当箇所」を
    示し、審査員が機械的に検索しても発見できる構造にする。

12. **Pコード対応表＋本文中のマーカーバッジは「必須」**
    5回目の指摘で判明: Pコード選択が正しくても、
    「機能説明資料の該当ページから機能が確認できない」と判定される。
    対策として:
    - 表紙・目次の直後に **「Pコード対応ページマップ」専用ページ**を新設し、
      各Pコードの機能例×本資料内の節／ページ番号 を一覧化した表を配置
    - 各機能サブセクション見出し直下に
      <span>共P-02 対応</span> / <span>共P-03 対応</span> の
      **黒太枠＋黄色／青色背景のマーカーバッジ** を配置
    審査員が任意のページから資料を確認しても、ページ単位でどのPコードに対応する
    機能なのかが一目でわかる状態にする。

13. **「取引内容」と「品名」を統合してラベル化する**
    6回目の指摘で判明: 適格請求書サンプルの明細表で「品名」「仕様」を別カラム化
    していると、審査員が「取引内容」というラベルを発見できず非対応と判定される。
    対策: 明細表のヘッダを **「取引内容（品名／仕様）」**に統合（黄色背景＋黒太枠）。
    軽減税率対象品目は行全体を緑色背景にして、「※ 軽減税率（8%）対象品目」マークを
    大型バッジで配置する。

14. **デモ機・テストアカウント情報は専用資料として用意する**
    6回目の指摘で判明: 審査員は実際に稼働確認できるかをチェックするため、
    ログインURL・テストアカウント（ID/PW）・選択Pコード別の機能確認手順を
    まとめた専用資料が「その他説明資料」として求められることがある。
    対策: `/subsidy/demo-info` を新設し、(a) サービスログインURL、(b) 3ロール
    （管理者／発注担当／受注担当）のID・パスワード、(c) Pコード別の確認手順、
    (d) セキュリティ注記 を網羅した PDF を用意する。

15. **「価格設定の内訳」入力テキストと PDF の文言を一致させる**
    6回目の指摘で判明: 申請ポータルの「価格設定の内訳」テキスト入力欄と
    アップロードした価格説明資料 PDF の表現に齟齬があると、カテゴリー混在と
    判定される。両者で「サポート・保守」「カスタマーサポート」等の文言を統一して
    除外し、「クラウドホスティング・SSL・日次バックアップは運用インフラとして内包」
    「カテゴリー7 保守サポート役務は含まない」を一致させること。

## 付録A: 申請書類 PDF化手順

1. Chrome 最新版で対象の `/subsidy/...` ページを開く
2. 右上の「🖨 PDFとして保存 / 印刷」または `Ctrl+P`／`⌘+P`

   - **送信先**: PDFとして保存
   - **用紙サイズ**: A4
   - **余白**: デフォルト（または標準）
   - **背景のグラフィック**: ✅ チェック（黒塗りヘッダ等を確実に印字するため）

- または TinyPNG 等で事前に画像を圧縮してから配置

現行の「受発注Lシステム」は インボイス対応類型（1機能 = 上限50万円）で登録済みだが、

#### 不採択理由の推定（登録要領・登録の手引きとの突き合わせ）

理由が通知されていないため、要領・手引きの要件と現行資料を逐条で突き合わせた結果、
**最も可能性が高いのは「導入事例・実績」要件の未充足**である。

**① 導入事例・実績が「過去の実績」でない（最有力）**

- ITツール登録要領 別紙1（1）2.⑥:
  「導入事例・実績 ※**過去の**導入事例・実績を説明したもの。」
- ITツール登録の手引き 3-5 価格説明資料 ❻: 同上。加えて「※URLのみの記載は不可」
- 手引きの**書式例**が示す水準:
  「【導入事例・実績】・20YY年MM月 導入社数 3000社達成 ・AA株式会社、BB会社、CCホールディングス」
- 手引きに明記: 「**※❸〜❼の項目で不備が頻発しています。提出前に精査してください**」（❻はこの範囲）
- **現行資料の状態**: 導入事例を「ハピネス建材株式会社（**想定**）」「サンライズフーズ株式会社（**想定**）」
  と明記している。これは「過去の実績」ではなく、要件を満たしていない。

**② 一般販売されていない製品と判定された可能性**

登録要領 2-3（1）2. ＩＴツール登録の対象外となるもの:

- (キ) ＩＴツールの登録申請時点において、**製品が完成しておらず、一般的に販売されていないもの**
- (サ) **特定の顧客向けに限定され、一般市場に販売されていないもの**

①（実績ゼロ）と組み合わせると、事務局側からは「まだ市販されていない製品」に見える。
別紙1（3）で事務局が追加提出を求められる資料の筆頭が
「**1. 過去にＩＴツールを販売した際の契約書**」であることも、この観点を裏づける。

**③ 不備訂正時の「修正箇所の明記」を怠っていた**

別紙1（2): 「事務局からの不備修正依頼を受けて資料を修正した際は、**資料内で前回からの修正箇所を明記すること**。」
4回の不備対応で、資料内に「前回からの修正箇所」を明示していなかった。単独では不採択理由にならないが、
再申請では必ず明記すること。

#### ④ 価格が市場価格を著しく上回ると判定されていた（もう一つの有力候補）

登録要領 2-3（1）9. 価格に関する留意事項:

> (ウ) 一般的な市場価格と比較して著しく高額である場合は、**ＩＴツール登録の対象外とする場合がある**。

そして 別紙1（1）3. 申請価格理由書:

> ※ 本理由書は、…**平均的な市場価格を大幅に上回る場合、提出を求める**。

**申請の途中で事務局から申請価格理由書の提出を求められている**（2026-08）。
これは事務局が当時点で「年額3,000,000円は平均的な市場価格を大幅に上回る」と
判定していたことを意味する。理由書を出しても納得が得られなければ 9.(ウ) により
対象外となる。**これは不備訂正で直る類のものではないため、理由を示さない不採択と整合する。**

#### ⑤ 「理由なしの不採択」の読み方

不備通知は4回来ている。資料の書き方で直る問題であれば5回目の不備通知が来たはずである。
理由を示さず不採択にしたということは、**不備訂正では直らない＝「登録の対象外」判定**
だったと読むのが自然。対象外になりうるのは ④（価格）と ②（一般販売されていない）。

なお、**受発注Lシステム（インボイス対応類型）は「サンプル商事株式会社（想定顧客）」表記の
まま登録に通っている**。したがって ①（想定の導入事例）だけが不採択理由とは言い切れない。
①は「直せる不備」であり、それが理由なら不備通知が来たはずである。
①は要件違反なので当然直すが、**本命は ④ と ② の組み合わせ**と考えるべき。

上記④への対応として、標準販売価格を **年額3,000,000円 → 年額2,400,000円** に改定した。

|---|---|---|
| 標準 | 250,000円／3,000,000円 | **200,000円／2,400,000円** |
| ミドル | 200,000円／2,400,000円 | **150,000円／1,800,000円** |
| 最小 | 150,000円／1,800,000円 | **100,000円／1,200,000円** |

補助額への影響は小さい:

価格説明資料・申請価格理由書・補助額試算はすべてそこから描画する。
資料側に金額をハードコードしないこと。**

#### 再申請にあたっての結論

**名称変更だけでは通らない可能性が高い。** 危険なのは
**「有償販売実績ゼロ」×「市場価格を大幅に上回る価格」の組み合わせ**であり、
どちらか一方を崩す必要がある。優先度は次のとおり:

1. **価格を下げる（実施済み・費用対効果が最も高い）** — 補助額の減少は30万円のみ。
2. **有償契約を1件でも締結する** — 別紙1（3）で事務局が追加提出を求められる資料の
   筆頭が「過去にＩＴツールを販売した際の契約書」であり、これがあれば ②④ 双方に反証できる。
   株式会社Cometa との有償契約（標準プラン 年額2,400,000円）を 2026年10月に予定しており、
   **締結後に申請するのが最も確実**。

加えて、導入事例欄については以下が必要:

1. **実在の販売実績をつくる**（1社でも有償契約を締結し、契約日・社名・金額を導入事例として記載する）。
   これが要件を正面から満たす唯一の方法。
2. 実績がまだない場合は、「導入事例・実績」欄に**書けることを正直に書く**
   （リリース日、提供開始時期、無償トライアル導入社数など事実ベースの数字）。
   **「（想定）」という表記は必ず削除する**。想定・仮定の事例は要件違反であり、
   かつ Playbook §8 の教訓「『仮例示』表記は絶対 NG」にも該当する。

#### 改名の実装（電子取引Lシステム → 電子取引くん）

**資料側にツール名をハードコードしないこと**（今回の改名で全箇所を定数参照に寄せた）。

ロゴ表記は「L」を含まない名称にも対応するため `logoBase` / `logoAccent` / `logoSuffix` の
3分割で保持する（受発注L = 受発注 + L + システム、電子取引くん = 電子取引 + くん + 空文字）。
