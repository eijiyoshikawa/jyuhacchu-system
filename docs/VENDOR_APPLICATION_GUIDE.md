⚠️ **無制限アカウント発行の契約は補助対象外**。価格資料に
「プラン別の受注側アカウント発行上限（例: 標準200社/ミドル100社/最小50社）」の表と
「上限なく発行できる契約ではない」旨を明記しておくこと（導入事例の招待社数と矛盾させない）。

**テンプレF（要件該当説明・446字）**（双方利用可→招待型無償→機能区分と利用状況管理→
一元管理→インボイス番号API検証→プラン別発行上限→電帳法対応、の順で全質問要素を1文ずつ回収する構成）:
> 電子取引Lシステムは、発注者（発注側企業）と受注者（受注側企業）の双方が利用できるクラウド型の電子取引プラットフォームです。発注側企業が契約し、取引先である受注側企業に対しては招待URLにより無償でアカウントを発行します（受注側の費用負担なし）。発注側・受注側のアカウントは機能が明確に区分され、発注側の管理画面では発行した招待と受注側アカウントの状況（招待中・受諾済み等）、取引先の事業者名・適格請求書発行事業者登録番号を一覧で管理できます。両社間では発注書・請求書等の商取引情報を電子的に授受し、契約（案件）・発注・請求を一元管理します。請求書は適格請求書等保存方式の必要記載事項に準拠し、登録番号は国税庁Web-APIで自動検証します。受注側アカウントの発行数には契約プランごとに上限（標準200社・ミドル100社・最小50社）を定めており、上限なく発行できる契約ではありません。電子帳簿保存法の電子取引要件（SHA-256ハッシュ+タイムスタンプ、検索3項目）にも標準対応しています。

### 6-4. ブランド一致の徹底（本申請最大の学び）

1つのアプリで複数ITツールを申請する場合、**審査員が見るすべての面**で申請ツール名に統一する:

- LP・資料ページの共通ヘッダ/フッタ（レイアウト分離: `(public)/_components/marketing-chrome.tsx`）
- デモ機のログイン画面・サイドバー・タブタイトル・利用規約（ホスト別ブランド: `src/lib/brand.ts`。
  ツールごとに専用ドメインを割り当て、**デモ案内は必ず専用ドメインのURL**で行う）
- 機能説明資料に埋め込む画面キャプチャ（他ツールのロゴが写った流用画像は不可。
  ツール別フォルダ `public/images/<tool>/` で管理）

## 7. 提出後の流れ

1. 審査は概ね1〜3週間で回転。**不備通知が来たら通知文全文を Claude に貼る** →
   `docs/APPLICATION_PLAYBOOK.md` §8（過去7回の不備対応・教訓15項目）と照合して資料修正 →
   PR → デフォルトブランチへマージで本番に自動反映 → PDF再出力 → 再提出
2. 頻出の不備パターン: ツール名/メーカー名が確認できない・業務フロー図がない・
   類似ツール比較に具体製品名がない・カテゴリー7混在・Pコード該当機能がページから確認できない・
   取引年月日/取引内容がサンプル帳票にない（詳細は Playbook §8-7）
